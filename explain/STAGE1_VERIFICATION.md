## 结论摘要

| 层 | 设计预期 | 实测结果 | 判定 |
|---|---|---|---|
| **估值** | 125 板块可用 | **127 板块 100% 可用**，PE 回溯到 2020 年 | ✅ **比预期更好** |
| **新闻** | 需过滤同源报道 | 126/126 覆盖，**平均 19.5 条独立报道** | ✅ **比预期更好** |

**设计必须修改：四层交叉检验 → 三层交叉检验（资金流 + 估值 + 新闻）。**

## 1. 估值层：超出预期

```
名称匹配: 127 / 127 估值板块 100% 匹配到资金流板块
PE 可用性: 126 / 126（100%）
历史深度: 回溯至 2020-08-24，1500 个交易日
```

**实例验证**（光伏设备）：
```
历史 PE: min 15.1 / p25 28.3 / 中位 46.3 / p75 58.9 / max 93.2
当前 PE: 44.4  →  历史分位 46%
```

结论：**PE 历史分位是本项目最坚实的估值锚**，可支撑完整分析。

> 附注：早期记录"125 个匹配"是因为加了日期过滤导致部分板块缺失，
> 无过滤时是 127 个且 100% 匹配。设计文档已更正。

## 3. 财报层：验证失败（这是本报告最重要的部分）

设计原计划：
```
板块成分股（push2 fs=b:BKxxxx）
      ×
个股财报数据（业绩快报/财务摘要）
      ↓
按成分股加权聚合成板块级财报
```

### 逐项实测结果

| 环节 | 实测 | 判定 |
|---|---|---|
| 板块成分股 | **20/20 板块可得**，中位 27 只成分股 | ✅ 可用 |
| 业绩快报（最新季） | 2026Q3 **仅 12 条**，覆盖全市场 **0.2%** | ❌ 不可用 |
| 业绩预告（近 3 月） | 原始 621 行 → **去重后 240 条 / 226 家公司 = 4%** | ❌ 覆盖极低 |
| 财务摘要 | 接口需特定过滤条件，按报告期批量取失败 | ❌ 未打通 |
| 业绩报表 `RPT_LICO_FN_CPD` | 接口不存在 | ❌ |

### 为什么覆盖这么低（根因）

**业绩快报是自愿披露**——只有少数公司会发快报，
绝大多数公司走正式季报/年报流程，而那些数据的批量接口我没能打通。

之前误以为"39512 条 = 覆盖充分"，实际那是**跨多个报告期的累计记录数**，
单看 2026Q3 只有 12 条。

**业绩预告还有第二个陷阱：大量重复行。**
实测近 3 月原始 621 行，但同一 (股票, 报告期) 会重复出现
（如"德明利"出现 4 次、"安凯微"出现 3 次）。按 (代码, 报告期) 去重后
**只剩 240 条 / 226 家公司 = 全市场 4%**。

若不去重，会高估覆盖率约 2.5 倍。

### 板块级覆盖率实测

```
半导体设备（25 只成分股）→ 有快报的仅 16 只（64%）
  但全市场 2026Q3 快报只有 12 条 —— 这 16 只的"快报"其实是旧报告期的
```

**即使按 64% 覆盖率硬算，聚合出的板块净利同比也是不可靠的**：
- 64% 的成分股不代表 64% 的市值
- 缺失的 36% 可能是最大权重的公司
- 缺失不是随机的（大公司和小公司披露习惯不同）

**结论：财报层不能做。** 硬做出来的"板块净利同比"是一个**看起来精确但实际不可靠**的数字，
比没有更危险。

**连降级方案也要打折**：业绩预告只有 4% 覆盖率，意味着绝大多数板块的
"财报层"会是空的。这本身就是一个诚实的结论：
**财报层在这个数据条件下，实际上等于不存在。**

## 4. 对设计的影响

### 修改前后对比

| | 原设计 | 修改后 |
|---|---|---|
| 层数 | 四层（资金流/估值/新闻/财报） | **三层**（资金流/估值/新闻） |
| 财报层 | 聚合板块净利同比 | **移除**，改为"财报日历"（只提示何时披露，不给数字） |
| 一致性打分 | 四票制 | **三票制** |
| 缺失处理 | 三层缺一层标"证据不足" | 财报层**始终标注不可得** |

### 财报层的降级方案（不是删除，是降级）

保留**能可靠做的部分**：

```
❌ 不做：板块净利同比（数据不可靠）
✅ 做：  财报预告清单 —— 「该板块有 N 家公司发布了业绩预告」
        数据源：业绩预告（需按 (代码,报告期) 去重）
        价值：**只在有数据时显示，没有就明说"该板块暂无预告"**
        ⚠️ 覆盖仅 4%，所以大概率是空的 —— 这恰恰说明不该假装有
```

这样财报层从"给出结论"降级为"给出日程"，**诚实且仍有用**。

## 5. 修改后的三层交叉检验

```
资金流（已有，496 板块 × 120 日）
    +
估值  （127 板块，PE 历史分位）
    +
新闻  （126 板块，平均 19.5 条独立报道）
    ↓
一致性判定（三票制）
```

**判定逻辑相应简化**：

| 组合 | 含义 |
|---|---|
| 资金流出 + 估值偏高 + 新闻偏空 | **三方一致** → 背离可信 |
| 资金流出 + 估值偏低 + 新闻偏多 | **三方矛盾** → 背离可能是错杀 |
| 资金流出 + 估值中性 + 新闻中性 | 证据不足 → 不下结论 |

财报层作为**独立的日程提示**显示，不参与打分。

## 6. 验证脚本附录

所有结论均由以下实测得出（脚本已在临时目录执行，关键逻辑如下）：

```python
# 估值匹配
ours = clist_all(FS_INDUSTRY)          # 494 板块
val  = RPT_VALUEINDUSTRY_DET           # 127 板块
matched = set(ours) & set(val)         # → 127（100%）

# 新闻覆盖
for name in matched:                    # 126 个
    search(name)                        # → 全部 100% 有结果
    filter(FLOW_SELFREF)                # → 平均保留 19.5 条

# 财报（决定性失败点）
fast_reports_2026Q3 = RPT_FCI_PERFORMANCEE filter REPORT_DATE='2026-09-30'
# → 仅 12 条 / 5778 只股票 = 0.2%
```

## 7. 最终判定

**继续做，但按三层设计。**

- ✅ 估值层：数据充足，是最坚实的锚
- ✅ 新闻层：覆盖良好，过滤规则已验证
- ❌ 财报层：**降级为日程提示**，不给数字
- ⚠️ 产业逻辑：仍只能代理，标注不变

**这个验证花的时间值了。** 如果按原设计做完，会在第四层发现数据不可靠，
而那时代码已经围绕四层写死，返工成本高得多。

—— 这正是设计文档第 10 节要求"先验证再开工"的原因。
